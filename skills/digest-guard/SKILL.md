# digest-guard

A schedule is a promise to keep doing something after everyone stops watching. The access-control check that gated the data when the schedule was *created* — a role, a row-level filter, a sandbox, a data-source grant — was correct at that moment, but a schedule's whole point is to keep running long after that moment, unattended, while every one of those inputs keeps changing underneath it: roles get downgraded, data sources get re-scoped, owners get deprovisioned, recipients get added. The bug isn't usually "access control is broken" — it's that nothing ever asks access control the question a second time.

## Check 1: is access checked once, or on every send?

Find where the schedule reads permission: at creation time only (stored as a flag, a cached grant, or simply never revisited), or freshly on every fire. A role downgrade, group removal, or row-level-security policy change made the day after a weekly digest was set up should show up in the *next* send — if it doesn't until someone manually re-saves the schedule, that's the core gap. Trace this concretely: does the send job re-run the underlying query/dashboard render through the live permission layer (same as if the recipient opened it in the UI right now), or does it reuse a query plan, cached result, or access token captured at schedule-creation time?

## Check 2: can someone self-subscribe into someone else's access?

List every way a recipient can be added to an existing schedule: an owner adding them, an admin bulk-adding them, and — the one teams forget to lock down — a "subscribe me to this" self-service action on a schedule someone else created. If self-subscribing just appends a row to a recipient list with no re-check of *whose* filtered view the schedule renders, a lower-privileged user can add themselves to a schedule built by someone with broader access and receive data their own row-level/sandbox restriction would never let them query directly. This is a real, patched vulnerability class, not a hypothetical: Metabase CVE-2023-23629 let a sandboxed (restricted) user add themselves as a recipient of another user's existing dashboard subscription and receive the creator's unfiltered data by email, and the related CVE-2023-23628 let a sandboxed user see who else was already subscribed — the schedule's own recipient list leaking who it was built around. Confirm self-subscription re-validates the *subscriber's* access against the content, not just that a recipient slot exists.

## Check 3: whose permissions does the render actually run under?

A schedule has (at least) two identities in play — the owner who built it and each recipient who receives it — and a frequent design bug is collapsing them into one. If the report renders once under the owner's access and the identical output is delivered to every recipient, then a recipient's own narrower access is irrelevant: they see everything the owner could see, by design, the moment they're added. Check which identity the render actually executes as, and whether that's documented and intended (an explicit "shared view" model) or an accident of implementation. Then check the owner side: Splunk's own documentation states plainly that scheduled reports and alerts only ever run as the owner, and that changing an existing schedule's permissions applies only to *future* runs — jobs already queued keep running on the old grant until someone manually intervenes through the job manager. If this system has the same run-as-owner shape, what happens when the owner is deprovisioned, downgraded, or has the underlying data source's access revoked? Does the schedule fail loudly, get disabled, or keep silently serving data on a grant that functionally no longer exists?

## Check 4: does the delivered artifact stay stale even after the data would be fresh?

Even a schedule that does re-check access live at send time can still ship stale data if the artifact itself — a rendered PDF, a CSV export, a cached image snapshot — was generated and queued before a permission change landed, then delivered after. Confirm the generation step and the permission-check step share one timestamp, not two: a "check access, then render from a pre-warmed cache" pipeline can pass the check against current rules while the cache it renders from still reflects the old ones.

## Report

BLOCK for: permission evaluated only at schedule-creation time with no re-check before send (Check 1); a self-subscribe path that adds a recipient without re-validating their own access against the content (Check 2, the CVE-2023-23629 shape); a render-once-under-the-owner design with no handling for the owner losing access (Check 3); or a cached/pre-rendered artifact that can ship stale rows even when the live permission check passes (Check 4). CAUTION for a re-check that exists but only covers the recipient's role, not row-level/sandbox filters layered underneath it, or an owner-deprovisioning path that disables new schedules but doesn't retract jobs already queued. Name the exact query, cache layer, or job-scheduling table involved — "permissions look fine" is not a finding; either every send re-evaluates access against both the owner's and each recipient's current state, or it doesn't.

## Boundaries

- Not `trail-guard`'s territory — that skill audits whether a mutating action gets logged at all. This skill assumes the schedule itself is fully legitimate and audits whether its *output* stays correctly scoped as access changes around it.
- Not `pref-guard`'s territory — that skill audits notification opt-outs and suppression lists (whether someone keeps getting a send they asked to stop). This skill audits whether the *content* of a send someone is still entitled to receive is the content they're actually still entitled to see.
- Not `export-guard`'s territory — that skill audits whether a one-off bulk export is complete and survives being opened (row-count caps, ID corruption in spreadsheets). This skill audits a *recurring* schedule's access correctness over its running lifetime, not a single export's completeness.
- Not `seat-guard` or `residency-guard`'s territory — those audit license-seat counts and data-location commitments respectively, not whether a report's content matches its recipient's current permissions.
- Doesn't design a BI tool's permission model from scratch — it audits whether an existing (or proposed) scheduled-delivery feature actually re-applies that model on every send, not which row-level-security or RBAC scheme to adopt.
- Can't observe a live production schedule's actual next-run output from source alone — it identifies whether the code's own re-check (or lack of one) is capable of serving stale access, and says plainly when confirming an actual leak needs inspecting real schedule/recipient data rather than a code read.
