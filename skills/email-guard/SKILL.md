Use when adding or reviewing an account-settings email-change (or phone/recovery-channel-change) endpoint, or when asked "does changing your email need your password", "do we notify the old address when someone changes their email", "can a stolen session take over an account by swapping the email", or "is our email-change flow safe".

# email-guard

An account's email address isn't just a contact field — it's the recovery channel: "forgot password" sends there, security alerts send there, and in a lot of apps it doubles as the login name. That makes a "change my email" endpoint a second, usually less-guarded front door to full account takeover: anyone who already has a live session for a few seconds — a stolen cookie, an XSS pop, an unattended laptop — doesn't need the password at all if they can just redirect the account's recovery channel to an address they control and lock the real owner out from there. The naive implementation (check the user is logged in, write the new address, done) treats this like any other profile edit, but it's really a sensitive security action wearing a settings-page costume, and the three checks that make a password reset safe — proof of identity, a signal to the party being changed away from, and holding the change until the new destination is proven reachable — usually never got copied over to it.

This is not a hypothetical. GitLab shipped exactly this gap for years: CVE-2018-19580 (tracked publicly as gitlab-org/gitlab-ce#39809) is a GitLab instance changing a user's email with no notification sent to the *old* address, fixed only in 11.5.1/11.4.8/11.3.11. More recently, Flowise's email-change flow (GHSA-x39m-3393-3qp4) let an unverified new address become the account's login/recovery address outright — an unverified email change *is* an account takeover, because nothing downstream checks that the new address is reachable by anyone but the attacker. Both are the same root cause from different angles: a sensitive change validated as a write, not as an identity transfer.

## Step 1: does changing the address require proving identity again?

Find the email-change endpoint/handler and check what it actually requires beyond an active session cookie or bearer token. Does it ask for the current password, or step up to MFA if the account has it enrolled, before accepting the new address — or does "you're logged in" count as sufficient proof on its own? A session is proof you were authenticated *at some point*; it is not proof you're still the account owner right now, and the whole value of a hijacked-session attack is that the attacker never needed the password to get that session. If there's no re-authentication step on this specific action, name that as the finding — not "is auth required" (it almost always is, trivially) but "is *this* action gated behind anything a cookie thief doesn't already have."

## Step 2: does the old address get told, and does the new one have to prove it's reachable before the change takes effect?

Two separate checks, both failure modes seen in the wild above:

- **Notification to the address being replaced.** When the change happens, does an email go to the *old* address saying so — the one and only channel the real account owner can still read if the new address is already the attacker's? A flow that only emails the new address (to "verify" it) tells the attacker, not the victim, and the victim finds out only when they can no longer log in. This is the exact CVE-2018-19580 gap: the new-address confirmation step existed, but nobody is watching the door the legitimate owner would notice something through.
- **Confirmation before the change is live.** Does the system hold the account on the *old* address until the new one clicks a confirmation link, or does it switch over immediately on submit and treat "new address verified" as a formality that happens later (or never)? If the new address becomes live before it's confirmed reachable, the account can be fully taken over by an address the attacker typo'd or doesn't even control yet, and there's no live old address left to recover through — the Flowise gap exactly.

## Step 3: what else should this sensitive action trigger that a plain profile edit wouldn't?

Check what happens immediately after a successful change: do other active sessions/refresh tokens get invalidated (so a session on a different device the real attacker doesn't control gets logged out, forcing re-auth with the new email), and is the change itself logged somewhere an owner reviewing account activity would actually see it (not just a silent row update)? Neither failing alone is the primary finding, but either missing compounds the blast radius of Step 1 or Step 2 already failing — note it as part of the same report rather than a separate concern.

## Report

BLOCK for: no re-authentication (password/MFA) required for this specific action beyond an existing session; no notification sent to the address being replaced; or the new address becomes the account's live/login address before it confirms receipt of anything (unverified-email-is-live-immediately, the Flowise shape). CAUTION for: re-authentication and old-address notification both present, but other sessions aren't invalidated after the change, or the change isn't visible in any account-activity log a real owner would check. Cite the exact handler and the exact step that's missing — "there's a confirmation email" is not the same claim as "the account stays on the old address until that email is clicked," and the report should say which one the code actually does.

## Boundaries

- Not `reaccept-guard`'s territory — that skill audits whether a ToS/policy re-acceptance gate reaches every surface (web, old mobile builds, the API). This skill audits a single sensitive settings action for account-takeover safety, not policy-version enforcement.
- Not `rotation-guard`'s territory — that skill audits whether rotating an *operational* credential (DB password, API key, Vault lease) propagates to every service consumer. This skill is about a *user's own* recovery channel being changed by (possibly) someone other than the account owner, a different actor and a different kind of "rotation."
- Not `push-guard`'s territory — that skill audits whether a push-notification device token outlives the logout that should have released it. This skill is about the email/phone-number field itself, not a device token.
- Doesn't extend to telecom-side SIM swapping or carrier account takeover — this skill audits the application's own email/phone-change code path, not the phone network the OTP rides over; a correctly-built flow here can still be defeated by a SIM swap upstream, and that's out of scope.
- Doesn't require every app to demand MFA step-up if the account never enrolled MFA in the first place — the finding in that case is "password re-entry is the available bar, and this action doesn't even clear that," not "add MFA." Don't invent a stronger standard than the account's own auth model supports.
- Can't confirm from source alone that the notification email is actually delivered in production (a broken mail provider, a spam-filtered send) — it audits whether the code's logic *attempts* the right sequence, and says so plainly rather than claiming delivery it can't observe.
