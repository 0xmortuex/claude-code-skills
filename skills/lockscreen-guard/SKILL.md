Use when adding or reviewing a new push/local notification type, a notification builder or wrapper, or when asked "does this notification respect hide-sensitive-content", "will this show on the lock screen", "audit our notification lock-screen redaction", or "why does this notification show full content when others don't".

# lockscreen-guard

The platform redaction APIs exist and most apps use them — for the *first* notification type someone built, while the platform guidance was open in another tab. Android's `NotificationCompat.Builder.setVisibility(VISIBILITY_PRIVATE)` paired with `setPublicVersion()`, or iOS's notification-content-extension/restricted-content gating, both correctly hide a message's real content behind the device's own "hide sensitive notifications" setting. What doesn't carry forward automatically is the second notification type: a different event, added months later by someone who copies the nearest existing send call that happens to predate the redaction work, or who never learned the redaction API exists because nothing forces every call site through it. It ships, it works, it looks identical to every other notification in testing (the test device is usually unlocked) — and it shows full content to anyone with physical access to a locked device, independent of whatever the user configured, because redaction has to be wired per call site and nothing enforces that it was.

This is not a one-off bug class — it is a mechanic that keeps reappearing across both major mobile platforms over more than a decade, because the failure mode is structural rather than a single library defect: **CVE-2020-0092** and **CVE-2026-0012** (Android, both rooted in `ExpandableNotificationRow.java`'s `setHideSensitive` handling, the 2026 one affecting Android 14/15/16 and fixed in the March 2026 security bulletin) show the identical code path mishandling redaction for a notification category years apart; **CVE-2025-22421** (Android, notification content descriptions exposed on the lock screen, bypassing visibility controls entirely) shows a different surface within the same OS leaking through a path the main visibility check never covered; **CVE-2026-28965** (Apple iOS/iPadOS, fixed in iOS/iPadOS 26.5) let an unauthenticated local user view restricted content from the lock screen that should only have been reachable after unlock; and **CVE-2014-4356** and **CVE-2015-7000** (both iOS, text-message and Notification Center previews respectively) show the OS itself failing to honor its own configured lock-screen-preview setting a decade earlier. Six independent, dated instances, both platforms, over eleven years — the pattern is that redaction coverage drifts per notification type and per OS release, not that any one of these was a freak one-off.

## Step 1: enumerate every notification type the codebase sends, and which call site each one goes through

Don't stop at the first (often best-maintained) notification code path found. Grep for every place that constructs and sends a user-facing OS notification — push-triggered, locally scheduled, or in-app-triggered — across every feature area, not just the messaging/chat feature that usually gets the most security attention. For each one, identify which builder/wrapper function it calls, and whether that's the same one the correctly-redacted notification type uses or a separately-constructed one.

## Step 2: for each notification type, check whether it actually sets the redaction fields — not whether some notification somewhere does

- **Android**: does this specific call site set `setVisibility(VISIBILITY_PRIVATE)` *and* provide a `setPublicVersion()` with a genuinely redacted summary (e.g. "New message" instead of the sender's name and text) — or does it fall through to the default `VISIBILITY_PUBLIC`, which shows full content on the lock screen regardless of the device's "hide sensitive notifications" setting? A notification channel's own default visibility matters too: a channel created with no explicit visibility, or one whose visibility a later code change silently widened, affects every notification posted through it.
- **iOS**: does this specific notification type route through a Notification Service Extension or Notification Content Extension that gates the real content behind unlock, or does its payload put the sensitive text directly in `alert.body`/`alert.title`, which the system will display on the lock screen as-is whenever the user's device-level "Show Previews" setting allows it?
- Trace this per notification *type*, listing each one's result explicitly — "type X: redacted correctly" / "type Y: no visibility/extension set, falls through to default" — rather than reporting a single pass/fail for "notifications" as a category. The whole point of this mechanic is that it's inconsistent across types, and a report that collapses them hides exactly the gap being hunted for.

## Step 3: find whether redaction was wired once and never carried forward

Identify the oldest or most actively maintained notification type in the codebase — it's usually the one that's correctly redacted, because it was built (or last touched) while someone had the platform guidance open. Then check every other type's call site: did whoever added it reuse the same builder/wrapper that sets the redaction fields, or did they construct a new builder/payload from scratch, or copy an older example that predates the redaction work? This is the exact shape behind CVE-2020-0092/CVE-2026-0012 and CVE-2025-22421: one code path in the same class handles a given category correctly, and a different category bypasses it entirely — not because anyone decided sensitive content should show, but because nothing routes every send through a single, enforced builder.

## Step 4: check the setting-change and new-channel/category edges

- If the user changes their device's "hide sensitive notifications" setting (or the per-channel/per-category visibility, where the platform exposes one) after a notification has already been delivered, does a currently-displayed or still-queued notification re-evaluate, or does the change only take effect for notifications sent afterward — CVE-2015-7000's exact shape, where the OS itself mishandled this transition?
- When a new Android notification channel or iOS notification category is created, what does it default to if the creating code doesn't explicitly set visibility/gating? A missing default that silently resolves to "public" is as real a finding as an explicit one — flag it the same way regardless of how deliberate it looks, the same fail-open principle `pref-guard` applies to delivery defaults, applied here to visibility defaults instead.

## Report

Lead with a per-notification-type table, not a single verdict: which types are correctly redacted, which fall through to the platform default, and which channel/category each depends on. **BLOCK** for any notification type carrying real sensitive content (a message body, a person's name, a balance, an OTP, a diagnosis) that ships with no `VISIBILITY_PRIVATE`+`setPublicVersion()` pairing on Android or no content-extension gating on iOS — name the exact call site and what it's missing relative to the type that does it correctly. **CAUTION** for a notification channel/category with no explicit visibility default (so a future addition inherits whatever the platform default happens to be rather than a deliberate choice), or for a setting-change edge (Step 4) that isn't confirmed either way. **SAFE** only with evidence: every notification-sending call site in the codebase routes through the same redaction-aware builder/wrapper (or was individually verified to set the fields correctly), and new-channel/category creation has an explicit, reviewed-in-code default rather than an implicit one.

## Boundaries

- Not `push-guard`'s territory — `push-guard`'s own Boundaries section explicitly disclaims this exact territory ("doesn't cover push payload encryption, lock-screen content redaction, or notification-permission-prompt UX"). This skill is that excluded piece: whether the content a push payload carries is actually gated from the lock screen once it arrives, not whether the device token or send path is correct.
- Not `recall-guard`'s territory — `recall-guard` treats "a lock-screen preview already showed the content" as a given constraint on recalling a message after the fact, and audits whether recall can reach it. This skill audits the question one step earlier: whether that preview should have shown full content at all, independent of any recall feature existing.
- Not `pref-guard`'s territory — `pref-guard` audits whether a user's channel/category opt-*out* (should this notification be sent at all) is honored. This skill assumes the notification is correctly sent and audits a different, orthogonal setting: how much of its content the OS is allowed to show on a locked screen.
- Not `clipboard-guard`'s territory — clipboard-guard is specific to the OS clipboard as a store; this skill is specific to the lock-screen notification surface, a different exposure point with different platform APIs.
- Can't verify what a specific OS version, OEM skin (Samsung/MIUI notification trays frequently diverge from stock Android), or a user's actual device-level setting currently does from source alone — platform behavior shifts across releases, same as the CVEs above show happening within the OS itself. State what the code sets and what the platform API allows; confirming the live on-device result needs a locked test device running the target OS version.
- Doesn't design a notification system or redaction architecture from scratch — reviews whether existing notification-sending code, across every type found in Step 1, actually uses the redaction mechanism consistently rather than only where someone happened to remember it.
