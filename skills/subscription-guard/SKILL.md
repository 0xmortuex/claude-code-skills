# subscription-guard

GraphQL subscriptions don't travel the same road as queries and mutations. A query or mutation arrives as an HTTP POST, so whatever auth middleware, decorator, or framework guard sits in front of the HTTP handler runs on every single one — there's no way around it. A subscription establishes a WebSocket connection instead, runs a separate protocol handshake (`graphql-ws` or the older `subscriptions-transport-ws`), and executes its resolver from a different code path end to end. If the team that wired up authorization did it once, at the HTTP layer, and never asked "does this also apply to the WS handshake and the subscription resolver's context," the subscription path can end up with weaker checks, stale checks, or no checks at all — while the query that returns the exact same field looks perfectly secured.

This is a real, recurring pattern, not a hypothetical: four independent GraphQL implementations — three libraries and one production SaaS platform — shipped this exact class of bug. Strawberry GraphQL's CVE-2026-35523 (GHSA-vpwc-v33q-mq89): the legacy `graphql-ws` subprotocol path could skip the framework's `on_ws_connect` auth hook entirely, letting a subscription connect and run with no authorization check at all even though the equivalent query was protected. Parse Server's CVE-2026-32594: the GraphQL subscription WebSocket endpoint never passed through the Express middleware chain that enforces auth, introspection limits, and complexity limits on the HTTP path — the maintainers' fix was to remove the feature rather than patch it, because the subscription transport simply wasn't on the same road as everything else. The Neo4j GraphQL library's CVE-2026-5423 (GHSA-fcpg-3fw5-vc65, CVSS 8.2): subscriptions accepted a JWT passed through `connectionParams` at connect time without verifying its signature, so a forged or tampered token passed straight into the resolver context even with authorization rules configured — the check existed, but the thing it checked wasn't actually validated. And in production, not just library code: GitLab's own HackerOne report #3049150 (closed 2025-11-14, fixed in GitLab 18.6, CWE-284) found that blocking a user correctly revoked the `access_api` policy GitLab's GraphQL HTTP controller checks — but GraphQL subscriptions run over ActionCable/WebSocket and never pass through that controller at all, so a blocked user's still-valid Personal Access Token kept receiving live issue, merge-request-reviewer, and CI-pipeline-status updates through subscriptions like `issuableAssigneesUpdated` and `ciPipelineStatusUpdated` indefinitely. Four different root causes (no hook at all, no middleware wiring, no signature check, and a policy check wired into one controller that a second transport's resolver path never passes through), same shape: the subscription transport is where authorization quietly stops applying.

## Step 1: find where (and whether) the subscription transport authenticates

Locate the WebSocket/subscription server setup — the `graphql-ws`/`subscriptions-transport-ws` config, the framework's subscription-specific connection hook (`onConnect`, `on_ws_connect`, equivalent) — and trace exactly how it establishes who's making the request:

- Is there an `onConnect`/connect-hook at all, or does the subscription server accept any WS handshake and hand it straight to the schema? A library that supports both the modern `graphql-ws` and legacy `subscriptions-transport-ws` subprotocols needs the hook wired on *both* — confirm it isn't only on the one the team tested with.
- Where does the identity come from — a cookie/session shared with the HTTP transport (which rides on the same auth the app already trusts), or a token passed through `connectionParams` in the WS payload? If it's `connectionParams`, is that token's signature actually verified (not just read as a claim and trusted), and is it re-validated for every message, not just accepted once at connect and cached?
- Does the connect hook's result actually reach the resolver's context — or does the resolver build its own separate context that re-derives (or skips) authorization independently of whatever the connect hook decided?

## Step 2: find whether the subscription resolver enforces the same rule as the query/mutation for the same field

A connect hook proves *someone* authenticated; it doesn't prove *this specific subscription* is allowed to receive *this specific data*:

- For every subscription field, find the query or mutation that returns the same underlying type or record, and compare their authorization logic side by side — a field-level directive, a resolver guard, or a service-layer check. If the query enforces "only the record's owner or a shared collaborator" and the subscription resolver has no equivalent check (or checks a coarser thing, like "is logged in" instead of "is allowed to see *this* record"), that's the gap.
- Is the authorization check re-evaluated on every event the subscription pushes, or only once when the subscription is first established? A user whose access is later revoked but whose subscription socket stays open can keep receiving pushed events under a permission check that only ever ran at subscribe time — the same connect-once trap, just one layer up from transport auth.
- For a subscription that filters or scopes events (e.g., "only this org's updates"), is that filter enforced server-side in the resolver/publish logic, or trusted from a client-supplied argument? A client that can pass an arbitrary `orgId` into the subscription argument and have the server filter by *that* instead of the authenticated user's own org turns a filtering convenience into an authorization bypass.

## Step 3: check what introspection and error paths leak independent of the above

- Does GraphQL introspection stay restricted (or disabled in production) on the subscription endpoint the same way it is on the HTTP endpoint — or did restricting introspection only ever get wired into the HTTP middleware, leaving the WS endpoint's schema fully introspectable (per the Parse Server shape, where subscriptions skipped the same middleware chain that also carried introspection/complexity limits)?
- Does a rejected or failed auth check on the WS handshake actually close the connection and stop delivering events, or does it log/warn and keep the socket open anyway — the same "found the bug but it doesn't actually block anything" failure mode as a logged-but-unenforced HTTP check?

## Report

Lead with whichever applies: (a) the subscription transport has no authentication hook at all, or has one that isn't wired for every subprotocol the server accepts — cite the specific gap in the connect/handshake code; or (b) authentication exists but the resolver-level authorization doesn't match the equivalent query/mutation's rule, or doesn't re-run per event. BLOCK for a subscription that delivers a field, record, or row a user couldn't reach through the equivalent query — this is a live, provable authorization bypass, not a theoretical one. CAUTION for a check that exists but is coarser than its HTTP equivalent (logged-in-only where the query requires per-record ownership) or isn't re-evaluated after the subscription is established. SAFE only with evidence: the connect hook validates a signed/verified token or shares the HTTP transport's session, that validation covers every subprotocol in use, and the resolver enforces the same per-record/per-field rule the equivalent query does — not just "the connect hook exists."

## Boundaries

- Not a GraphQL build/design skill — doesn't design a subscription schema, a pub/sub backend, or scaling fan-out from scratch; reviews whether an existing subscription's authorization actually matches its HTTP-path equivalent.
- Not `overwrite-guard`'s, `pagination-guard`'s, `reaccept-guard`'s, `sunset-guard`'s, `throttle-guard`'s, or `trail-guard`'s territory — each of those mentions GraphQL only incidentally, as one API surface among several for a concern (version checks, pagination, re-acceptance gates, sunset notices, rate limits, audit logging) that applies equally to REST; this skill is specifically about the authorization split between the HTTP and WebSocket transports of the *same* GraphQL schema.
- Not `revoke-guard`'s territory at the generic WebSocket layer — that skill audits whether revoking access closes an already-open realtime-collaboration socket for any WS-based app. This skill is GraphQL-specific: it audits whether the subscription transport's authorization ever matched the HTTP transport's in the first place, which is a different failure (a split that existed from day one, not a revocation that failed to propagate) — though a GraphQL subscription that re-checks access only at connect time and never again is an instance of both gaps, and the Report should name it under both angles if it applies.
- Doesn't audit GraphQL query/mutation cost limiting, depth limiting, or batching abuse — those are rate-limit/complexity concerns `throttle-guard` or dedicated GraphQL-security tooling cover; this skill is narrowly about authorization parity between transports.
- Can't verify a production WS gateway's actual subprotocol negotiation or a load balancer's handling of long-lived connections from source alone — say plainly when confirming which subprotocol clients really use needs a live trace, not just a code read.
